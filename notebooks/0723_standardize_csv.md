# ［BUILD］プレートリーダーCSV標準化プログラムの設計方針

## 問題の確認

プレートリーダー由来のCSVを、次の統一形式へ変換する。

* `plate_id`
* `well`
* `variant_id`
* `replicate`
* `signal`
* `control_type`
* `screening_round`

さらに、次の異常を明示的に検出する。

* 必須列がない
* ウェル名が不正
* 測定値が数値でない
* 同じウェルが重複している
* 必要な対照ウェルがない

この課題は単なるCSV変換ではない。

> 不均一な実験データを、後続の解析が信頼できる標準形式へ変換する入口を作る

ことが目的である。

---

# 1. 基本設計思想

処理を次の4段階に分ける。

1. CSVを読み込む
2. 列名や文字表記を標準化する
3. データの妥当性を検証する
4. 統一形式のDataFrameを返す

重要なのは、すべてを一つの巨大な関数に詰め込まないことである。

異常の種類ごとに、次のような責務へ分割する。

* CSVを読み込む処理
* 列名を変換する処理
* 必須列を検証する処理
* ウェル名を検証する処理
* 測定値を検証する処理
* 重複ウェルを検出する処理
* 対照ウェルを検証する処理

この分割には次の利点がある。

* どの規則で失敗したかが明確になる
* 一つの検証規則だけを個別にテストできる
* 384ウェルプレートなどへ拡張しやすい
* メーカーごとのCSV形式を吸収しやすい
* バグが発生した場所を特定しやすい

---

# 2. ディレクトリ構成

今回の段階では、次の構成が適切である。

* `data/raw/`

  * プレートリーダーから出力された元CSV
* `data/processed/`

  * 統一形式へ変換したCSV
* `src/molecular_screening/exceptions.py`

  * プロジェクト固有の例外クラス
* `src/molecular_screening/plate_reader.py`

  * CSVの読み込み・変換・検証
* `tests/test_plate_reader.py`

  * 各検証規則のテスト
* `pyproject.toml`

  * pandasやpytestなどの依存関係
* `README.md`

  * 入力形式、検証規則、実行方法

生成されたデータとプログラム本体を同じ場所に置かないことが重要である。

---

# 3. 最初にデータ契約を決める

7列を単なる列名としてではなく、各行が守るべき契約として定義する。

| 列                 | 意味                      | 想定する型    |
| ----------------- | ----------------------- | -------- |
| `plate_id`        | プレート識別子                 | 文字列      |
| `well`            | ウェル位置                   | 文字列      |
| `variant_id`      | 変異体識別子                  | 文字列または欠損 |
| `replicate`       | 反復番号                    | 整数       |
| `signal`          | プレートリーダー測定値             | 浮動小数点数   |
| `control_type`    | sample、blank、positiveなど | 文字列      |
| `screening_round` | スクリーニングラウンド             | 整数       |

さらに、次のような規則を事前に決める。

* 通常サンプルでは`variant_id`を必須とするか
* 対照ウェルでは`variant_id`を空にしてよいか
* `replicate`は1から始めるか
* `signal`の欠損を許可するか
* 負の測定値を許可するか
* 必要な対照の種類は何か
* 同一プレート内でウェル位置を一意とするか

これらはPythonが自動的に決めるものではない。実験設計に基づいて決める。

---

# 4. 生CSVと統一形式を分離する

実際のプレートリーダーCSVは、最初から統一列名になっているとは限らない。

例えば、機器によって次のような列名が使われる可能性がある。

* `Plate`
* `Well Position`
* `Sample`
* `Repeat`
* `RFU`
* `Type`
* `Round`

これらを内部では次の統一名へ変換する。

* `Plate` → `plate_id`
* `Well Position` → `well`
* `Sample` → `variant_id`
* `Repeat` → `replicate`
* `RFU` → `signal`
* `Type` → `control_type`
* `Round` → `screening_round`

重要なのは、特定機器の列名を処理本体へ直接埋め込まないことである。

列名の対応関係を独立して管理すれば、別の機器を使う場合にも変換規則だけを変更できる。

---

# 5. 独自例外を定義する

すべてを一般的な`ValueError`で表現するのではなく、異常の種類ごとに例外を分ける。

想定する例外は次のとおり。

* `PlateDataError`

  * プレートデータ関連の基底例外
* `MissingRequiredColumnsError`

  * 必須列が不足している
* `InvalidWellError`

  * ウェル名が不正
* `InvalidSignalError`

  * 測定値が数値でない
* `DuplicateWellError`

  * 同一ウェルが重複している
* `MissingControlError`

  * 必要な対照ウェルがない

基底例外を用意する理由は、上位処理ではプレートデータに関する例外をまとめて捕捉できる一方、テストでは具体的な異常種別を区別できるからである。

---

# 6. 検証の順序

検証は次の順番で行う。

## 6.1 必須列の検証

最初に、必要な7列が存在するか確認する。

列が不足している状態では、後続の検証処理そのものが成立しないためである。

エラーには、不足している列名をすべて含める。

例：

* `signal`がない
* `control_type`と`screening_round`がない

単に「列がありません」とするのではなく、何が不足しているかを明示する。

## 6.2 文字表記の標準化

同じ意味の値を同じ表記へ揃える。

ウェル名では、例えば次を同じ値として扱う。

* `A1`
* `A01`
* `a1`
* 前後に空白を含む`A1`

標準化後は`A1`へ統一する。

`control_type`も次のような違いを吸収する。

* `Blank`
* `BLANK`
* `blank`
* 前後に空白がある値

標準化後は小文字の`blank`へ統一する。

重複検査より前に標準化する理由は、`A1`と`a01`を別ウェルと誤認しないためである。

## 6.3 測定値の検証

`signal`列の各値が数値へ変換できるか確認する。

不正値の例：

* `missing`
* `not measured`
* 空文字
* 単位付きの文字列
* 数字に見えるが変換できない文字

不正値がある場合は、次をエラーに含める。

* CSV上の行番号
* 不正な値
* 必要であればプレートIDとウェル名

これにより、元CSVのどこを修正すればよいか分かる。

## 6.4 ウェル名の検証

96ウェルプレートの場合、有効な位置は次の範囲である。

* 行：AからH
* 列：1から12

有効例：

* `A1`
* `B7`
* `H12`

不正例：

* `I1`
* `A13`
* `AA1`
* `1A`
* 空欄

384ウェルプレートを将来扱う場合は、行と列の範囲が変わるため、プレート形式を設定として分離できる設計が望ましい。

## 6.5 重複ウェルの検証

「同じウェル」の定義を最初に決める必要がある。

初期設計では、次の3項目がすべて同じ場合に重複と判断する。

* `screening_round`
* `plate_id`
* `well`

同じウェル位置でも、別のプレートや別ラウンドなら重複ではない。

重複を検出した場合は、該当するすべての行をエラー情報に含める。

将来、同じウェルを時間差で複数回測定するなら、次のような列が必要になる。

* 測定時刻
* 波長
* 測定サイクル
* 測定条件

その場合は、重複の定義も変更する。

## 6.6 対照ウェルの検証

対照ウェルは、プレート単位で検証する。

例えば、各プレートに次の3種類を必須とする。

* `blank`
* `positive`
* `negative`

ただし、必要な対照の種類は実験ごとに異なる。

ある実験では、

* blank
* positive

だけでよい可能性もある。

したがって、必要な対照種別はプログラムへ固定せず、設定または関数の引数として変更できる設計が望ましい。

---

# 7. 処理全体の責務

CSVを処理する中心関数は、細かな検証ロジックを直接持たず、処理順序を管理する役割にする。

中心関数が担当するのは次の流れである。

1. CSVを読み込む
2. 必要に応じて列名を変換する
3. 必須列を検証する
4. 統一列だけを取り出す
5. 文字列を標準化する
6. 測定値を検証する
7. ウェル名を検証する
8. 重複ウェルを検証する
9. 対照ウェルを検証する
10. 検証済みDataFrameを返す

中心関数を読んだだけで、処理の流れが把握できる状態を目指す。

---

# 8. ログと例外の役割分担

検証関数では、異常を発見したら具体的な例外を発生させる。

ログは、最上位の実行部分で一度だけ記録する。

役割分担は次のようにする。

## 下位の検証関数

* 異常の内容を特定する
* 適切な例外クラスを選ぶ
* 詳細なメッセージを付けて例外を発生させる

## 最上位の実行部分

* 例外を一度だけログへ記録する
* プログラムを終了する
* またはユーザーへ修正を要求する

各階層で同じ例外をログへ書くと、一つの異常が何度も記録されるため避ける。

---

# 9. テストの設計思想

最初に正常なデータを一つ用意する。

その正常データを基準として、各テストでは一か所だけを壊す。

必要なテストは次のとおり。

* 正常なCSVを読み込める
* 必須列不足を検出できる
* 不正なウェル名を検出できる
* 数値でない測定値を検出できる
* 同一ウェルの重複を検出できる
* 必要な対照不足を検出できる
* 列名を統一形式へ変換できる
* ウェル名の大文字・ゼロ埋めを正規化できる
* 列順を統一できる

各テストで一つの規則だけを壊す理由は、テスト失敗の原因を明確にするためである。

複数の異常を同時に含むデータでは、どの検証で停止したのか分かりにくくなる。

---

# 10. 実装の進め方

一度にすべてを完成させない。

## 第1段階：正常系を通す ✓

最初に、正常なCSVを読み込んで7列を正しい順番で取得できるようにする。

この段階では、複雑な例外処理を実装しなくてよい。

合格条件：

* CSVを読み込める
* 7列を抽出できる
* DataFrameを表示できる
* 列順が統一されている

## 第2段階：必須列の検証 ✓

不足している列を特定し、明示的な例外を出す。

合格条件：

* 一列不足を検出できる
* 複数列不足を検出できる
* 不足列名がエラーメッセージに含まれる

## 第3段階：ウェル名の標準化と検証 ✓

表記揺れを統一してから、有効範囲を確認する。

合格条件：

* `a01`を`A1`へ変換できる
* `H12`を受理できる
* `I1`や`A13`を拒否できる

## 第4段階：測定値の検証 ✓

数値変換できない値を検出する。

合格条件：

* 整数を受理できる
* 小数を受理できる
* 数値文字列を受理できる
* `missing`などを拒否できる
* 不正行を特定できる

## 第5段階：重複検出 ✓

同じラウンド・プレート・ウェルの組合せを検出する。

合格条件：

* 同じプレート内の重複を拒否できる
* 別プレートの同じウェルを受理できる
* 別ラウンドの同じウェルを受理できる

## 第6段階：対照ウェルの検証　✓

プレートごとに必要な対照が揃っているか確認する。

合格条件：

* 必要な対照が揃ったプレートを受理できる
* 一種類不足した場合に検出できる
* どのプレートで何が不足したか表示できる

## 第7段階：pytestを追加する ✓

各検証規則について自動テストを書く。

合格条件：

* 正常系テストが通る
* 各異常系テストが期待した例外を確認する
* すべてのテストを一つのコマンドで実行できる

# 11. 最初に作る入力データ

最初のCSVは、実際の96ウェル全体である必要はない。

最低限、次を含む小規模データでよい。

* 通常サンプル
* blank対照
* positive対照
* negative対照
* 同じ変異体の反復測定
* 数値のsignal
* 一つのplate_id
* 一つのscreening_round

最初から96行作ると、ロジックよりデータ入力作業に時間を取られる。

まず5〜10行程度の正常データで処理を通し、その後に異常データを個別に作る。

# 13. このBUILDで身につけるべき本質

この課題の本質は、pandasの操作を暗記することではない。

次の考え方を習得することにある。

* 生データと解析用データを分離する
* データ形式を契約として明文化する
* 表記揺れを正規化してから比較する
* 不正データを黙って補正しない
* エラーの種類を区別する
* 後続処理が信頼できる入口を作る
* 一つの関数に複数の責務を持たせない
* 正常系を作ってから異常系を追加する
* 実験上の規則とPython上の処理を区別する
* 検証規則を自動テストで固定する

最初から完成形を目指すのではなく、

> 正常なCSVを一度通す
> → 一つの異常を検出する
> → テストで固定する
> → 次の異常へ進む

という反復で進める。
